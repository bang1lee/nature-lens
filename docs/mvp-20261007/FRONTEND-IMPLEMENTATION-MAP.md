## 2. 읽기에서 확인한 구체적인 개선 지점

- `MobileApp.navigate()`는 webBoard의 `home`을 `records`로 바꾼다. 그러나 웹 보드에도 홈과 내 기록 버튼이 모두 있어 같은 목록으로 이동한다. 보드 메뉴는 **관찰 보드 / 컬렉션 / 예시 저널 / 저장과 백업 / 출판 작업실**처럼 목적을 분명히 한다. `/mobile/` 홈은 기존대로 남긴다.
- 보드의 `filtered`는 생물군·컬렉션·검색만 처리한다. 검수 상태 필터가 없다. `Studio`에는 검수 상태가 있으므로 명칭과 판정을 통일한다. 검수 완료의 출판 가능 판단에는 `canPublish()`를 재사용한다.
- 보드 0건 문구는 `query`만 본다. 생물군 또는 컬렉션 때문에 0건이면 “첫 번째 발견”으로 오인할 수 있다. 전체 기록이 0건인 상태와 조건 결과가 0건인 상태를 `records.length`와 활성 조건으로 나눈다.
- `navigate()`는 검색·컬렉션을 지우지만 생물군은 유지한다. 필터 유지/초기화 규칙을 명시하고 “조건 초기화”는 검색·생물군·검수 상태·컬렉션을 모두 초기화해야 한다.
- 기존 `.m-tabbar`는 1024px 이상에서 왼쪽 세로 메뉴로 바뀌지만 절대 위치이고 `.m-content`의 고정 왼쪽 여백에 의존한다. 새 보드는 탐색 열과 내용 열의 안정적인 레이아웃으로 정리하고 200% 글자 확대에서 겹치지 않게 한다.
- `.m-web-board .m-stage`는 현재 DOM과 맞지 않는다. `m-web-board`와 `m-stage`가 **같은 최상위 요소**에 붙어 있으므로 해당 배경을 고칠 때 `.m-stage.m-web-board` 또는 `.m-web-board`를 사용한다.
- 1024px 이상 `.m-stage`, `.m-app`, `.m-content` 규칙은 `/mobile/`에도 적용된다. 보드 작업 때문에 공통 규칙을 무심코 바꾸면 기존 모바일 미리보기·캡처·저널이 함께 달라진다. 보드용 변경은 `.m-web-board` 아래로 한정하는 선택이 안전하다.
- 상세의 “출판 작업실에서 이어하기”는 지금 `/`만 연다. 사용자가 보고 있던 기록까지 자동으로 여는 동작은 없다. 현재 안내를 유지하거나, Opus가 선택하면 `/?record=<id>`처럼 **기록 ID만** 전달하고 Studio가 로컬 목록 로드 후 그 기록을 여는 작은 연결을 추가한다. 사진·이름·키는 URL에 넣지 않는다. 기록 삭제/없는 ID/새 주소의 빈 DB는 목록과 안내로 돌아간다.
- `Studio.save()`는 DB 저장 후 목록 갱신에 실패하면 편집창이 남을 수 있다. 성공한 저장과 실패한 갱신을 구분해야 재저장 때 충돌로 오인하지 않는다. `MobileApp.afterSave()`와 `BackupPanel`에는 이미 두 상태를 나누는 안내가 있다.
- `Editor`는 네이티브 `<dialog>`와 Studio의 초점 복원을 이미 사용한다. 대화상자 라이브러리를 새로 넣기 전에 기존 동작을 유지·검증한다. 닫기 때 미저장 변경 확인은 QuickCapture에 있고 Editor에는 없으므로, 편집창 구조를 바꾼다면 미저장 변경 처리 여부를 함께 결정한다.
- `Studio.backup()`의 “내려받았습니다”는 다운로드 완료를 실제로 감지하지 않는다. `BackupPanel`처럼 “다운로드를 요청했어요. 파일 저장 여부를 확인해 주세요.”가 실제 동작에 맞는다.

## 3. 화면별 수정 파일과 완성 모습

### A. 데스크톱 관찰 보드

**주 파일:** `src/components/mobile/MobileApp.tsx`, `src/components/mobile/mobile.css`. 경로 자체는 `src/app/board/page.tsx`에 유지한다.

1440px에서 왼쪽 탐색은 약 220~240px, 본문은 남은 너비를 사용한다. 전체 레이아웃은 `minmax(0, 1fr)`처럼 내용 열이 좁아질 수 있게 만들고, 긴 제목·메모로 가로 스크롤이 생기지 않게 한다. 상단에는 “내 관찰 보드”, 기록 수, 짧은 로컬 보관 설명, 주요 행동 **관찰 추가**를 둔다. 시작 화면에 큰 마케팅 배너나 중복 촬영 버튼을 추가하지 않는다. 가상 예제는 사용자가 선택해 불러오게 한다.

도구 영역은 검색, 생물군, 검수 상태, 컬렉션, 조건 초기화 순서로 묶는다. 각 입력에 보이는 이름과 접근 가능한 레이블을 제공한다. 결과 수는 “전체 12건 중 4건”처럼 조건과 연결한다. CSS 그리드는 1440px에서 사진을 충분히 볼 수 있는 3~4열, 1024px에서 2~3열, 390px에서 1~2열을 내용 최소 너비에 따라 선택한다. 카드는 사진→날짜·상태→제목→종 이름/관찰 문장→컬렉션 맥락 순서이며 사진 위 질감·짙은 글자 오버레이를 피한다.

**보존:** 정렬은 현재 `updatedAt` 내림차순이다. 관찰일 정렬로 바꿀 경우 별도 명시하며 조용히 의미를 바꾸지 않는다. 예제의 `demo` 표시와 실제 기록 수의 구분을 유지한다. 레퍼런스는 Padlet의 단일 시작 행동, iNaturalist의 가까운 필터·상세 연결, Are.na의 사진과 컬렉션 맥락이다.

**연결 검사:** 기존 `tests/web-camera.spec.ts`, `tests/e2e/mobile.spec.ts`; 제안 `tests/e2e/board.spec.ts`에 검색·생물군·검수·컬렉션의 교집합, 전체 초기화, 첫 방문/조건 0건, 작업실 링크를 추가한다.

### B. 관찰 추가와 저장 성공

**주 파일:** `QuickCapture.tsx`, 보드 전용 `mobile.css`; `WebCamera.tsx`는 권한·종료 수정이 필요한 경우에만 좁게 변경한다.

넓은 화면에서 사진 미리보기와 입력을 2열로 제공하고 사진 선택/카메라 켜기 선택을 명확히 한다. 이름·메모는 선택이며, 도움말은 “잎의 모양, 색, 주변에서 발견한 특징을 적어 보세요”처럼 실제 관찰을 돕는다. 생물군·지역·GPS는 이름 필수화를 대신하는 장벽이 되지 않게 한다. 추가 설명은 접을 수 있어도 현재 위치 비공개/정밀 좌표 보관 선택의 의미를 숨기지 않는다.

저장 버튼은 준비 중·저장 중·완료·실패를 구분한다. 파일 선택 후 사진 준비가 실패하면 재선택할 수 있고, 저장 실패 시 사진·메모를 유지한다. 성공 화면은 “방금 기록 보기 / 하나 더 기록하기 / 관찰 보드로”를 제공한다. `/mobile/`의 기존 “홈으로”는 보존하거나 해당 테스트와 함께 변경한다. 카메라를 여는 것과 사진 저장을 같은 이벤트에 섞지 않는다.

**연결 검사:** `tests/e2e/mobile.spec.ts`의 파일 오류·닫기 취소·뒤로 가기, `tests/e2e/community.spec.ts`의 GPS 선택/거절, `tests/web-camera.spec.ts`의 스트림 종료·늦은 권한 허용을 유지한다.

### C. 관찰 상세와 출판 편집 연결

**주 파일:** `MobileApp.tsx`, `mobile.css`, 필요 시 `Studio.tsx`. 상세를 분리한다면 제안 신규 `src/components/board/ObservationDetail.tsx`; 공유 데이터 형식은 그대로 사용한다.

1440px에서 큰 사진과 관찰 메모/이름/날짜/초안 상태가 동시에 보이는 2열을 만든다. 390px에서는 사진 뒤에 내용이 오는 1열이다. 원본 전체를 볼 수 있는 사진 비율은 상세에서 `object-fit:contain`으로 보존하고 카드 미리보기의 잘림과 구분한다. “검수·기록집 편집” 링크를 주요 후속 행동으로 둔다. 검수 완료라는 글자는 색상과 함께 제공한다.

미설정 AI 이름 찾기는 수동 기록을 막지 않는 작은 안내이며, 후보를 만드는 가짜 결과를 넣지 않는다. 현재 `IdentificationPanel`의 계약과 Supabase 준비 조건은 그대로 보존한다. `PrivateLocationNote`의 정밀 위치 삭제 기능을 숨기지 않는다. 상세→목록 전환 후 호출한 카드에 초점을 돌려주고, 촬영/상세가 닫힐 때 탐색 위치를 예측 가능하게 한다.

**연결 검사:** 기존 `tests/app-platform.spec.ts`의 후보/취소/오류/미설정 상태, `tests/storage.test.ts`의 위치 삭제·사진 교체, 제안 board 검사에서 상세 2열/1열 및 작업실 연속 편집을 확인한다.

### D. 컬렉션과 작업실

**주 파일:** `MobileApp.tsx`, `Studio.tsx`, `globals.css`, `mobile.css`.

보드 메뉴에 컬렉션 접근을 독립적으로 제공한다. 기존 컬렉션 목록→해당 기록 필터 동작을 유지한다. 컬렉션 생성은 이미 Studio에 있으므로 보드에 입력기를 중복 생성하기보다 작업실 생성 위치를 먼저 명확히 연결한다. 보드에서 바로 생성하는 방식을 Opus가 택하면 `collectionWriteSchema`와 `saveCollection()`을 동일하게 사용한다.

작업실 상단에는 “관찰 보드로” 실제 링크를 추가한다. 검수·출판은 기존 Studio/Editor/Book에서 이어간다. 기록이 쌓인 작업실은 긴 소개 영역을 줄여 도구와 사진 목록이 바로 보이게 한다. 초기 방문 도움말은 전체 빈 상태에서만 강조하고 매 방문 거대한 소개를 반복하지 않는다. 새 이름이 필요해도 기존 기록 ID·컬렉션 ID를 바꾸지 않는다.

**연결 검사:** `tests/e2e/studio.spec.ts`의 컬렉션 생성·검색·편집 초점 복원, `tests/collection-name.test.ts`의 이름 정규화·과거 컬렉션 읽기 규칙.

### E. 편집·검수·기록집

**주 파일:** `Editor.tsx`, `Book.tsx`, `globals.css`. 데이터 조건은 `domain.ts` 그대로 재사용한다.

편집창은 사진 왼쪽/입력 오른쪽을 유지하며 좁은 화면에서 한 열로 내려간다. 초안 저장과 검수 완료 저장을 분명히 구분한다. 모든 수정은 다시 초안이 되는 현재 규칙을 유지한다. “식물 이름”은 곤충·기타 기록에도 쓰이므로 “생물 이름”처럼 데이터 범위에 맞게 문구를 바꿀 수 있지만 저장 필드 `species`는 변경할 이유가 없다.

기록집은 수록 조건, 표지 제목, 컬렉션 범위, 수록 순서, 실제 A4 미리보기를 유지한다. 내보내기는 현재 브라우저 인쇄/PDF이며 별도 서버 PDF 생성으로 바꾸지 않는다. 모바일 예시 저널과 사용자가 만든 실제 기록집은 서로 다른 화면임을 명시한다.

**연결 검사:** `tests/domain.test.ts`, `tests/e2e/studio.spec.ts`, `tests/production-smoke.mjs`의 표지+검수 기록 PDF 2페이지와 예시 저널 6페이지. 제목·본문이 긴 실제 데이터에서 잘림도 시각 확인한다.

### F. 저장과 백업·암호화 임시 전달

**주 파일:** `Studio.tsx`, `BackupPanel.tsx`. 제안 신규 `src/components/BackupTransferPanel.tsx`, `src/lib/transfers/client.ts`, `src/lib/transfers/crypto.ts`, 수신 경로 `src/app/transfer/page.tsx` 또는 Opus가 확정한 경로. 새 파일은 이 조사 시점에 구현되지 않았다.

같은 설정 화면에서 “파일로 보관”과 “다른 기기로 임시 전달”의 목적을 나란히 설명한다. 파일 백업은 인터넷 없이 동작하고 최대 50MB의 복원 파일을 받는다. 임시 전달은 더 작은 서버 한도(현재 Astra 제안 암호문 1MiB), 만료, 사용자 조기 삭제, 링크를 가진 사람의 접근 가능성을 별도로 안내한다. 서버가 준비되지 않거나 오프라인이면 임시 전달만 비활성화하고 파일 백업은 유지한다.

생성 UI는 준비→암호화→전송→링크 생성→복사/삭제 상태를 분리한다. 실패하면 원본 로컬 기록이 유지되고 파일 백업을 안내한다. 수신 UI는 링크 확인→내려받기→복호화→백업 내용 확인→사용자가 복원 선택→완료로 진행한다. 처음 링크를 열었다는 이유만으로 기존 자료를 변경하지 않는다. URL fragment(주소의 # 뒤에서 서버 요청에 포함되지 않는 부분)에 키·읽기 토큰을 보관하고, 외부 메신저 전송 버튼을 자동 실행하지 않는다. 키가 담긴 주소를 분석 로그나 화면 캡처 결과 이름에 넣지 않는다.

수신 JSON은 기존 `restoreBackupFile()` 경로로 전달해 사진 재처리·중복 보존·초안 재검수를 그대로 적용한다. 기능 전용 버튼은 Worker `/api/capabilities` 응답에 맞추고, 기존 엄격한 AI `capabilitySchema`에 일반 기능 필드를 섞지 않는다. Worker·D1 구현 담당자와 정확한 응답 타입·오류·만료 정책을 공유한다.

**연결 검사:** 기존 `tests/backup.test.ts`, `tests/e2e/integration.spec.ts`. 제안 신규 `tests/transfers.test.ts`와 `tests/e2e/transfers.spec.ts`에서 서로 다른 브라우저의 복원, 잘못된 키/변조, 만료·삭제, 초과 크기, 오프라인에서도 파일 백업 유지, fragment 비전송을 확인한다. 보안·서버 검사는 백엔드 담당자의 추가 검사와 함께 완료해야 한다.

## 6. 스타일 적용 순서와 접근성

1. `globals.css`의 기존 CSS 변수와 `mobile.css`의 `--m-*`가 서로 다른 색을 사용한다. paper `#F5F2E9`, card `#FFFEFA`, ink `#213D32`, forest `#254F3B`, secondary `#526353`, review `#D8CC84`를 의도한 역할에 연결하되 두 파일 전체를 한 번에 재작성하지 않는다. `design-system/README.md`의 Figma 명세는 아직 앱 전면 적용의 증거가 아니다.
2. `.m-web-board` 탐색/본문→도구→카드→상세→촬영→설정 순으로 좁게 스타일을 적용한다. 공유 스타일 수정은 `/mobile/`와 `/`의 브라우저 검사 후 확장한다. `.m-primary`/전역 `button` 선택자로 모든 버튼을 동시에 바꾸지 않는다.
3. 보이는 레이블, 최소 48px 주요 동작, 충분한 입력 경계 대비, 키보드 초점, 동작 감소를 유지한다. 1440/1024/390/320px과 200% 글자 확대에서 가로 넘침·메뉴 겹침을 확인한다. 예쁜 화면 캡처만으로 접근성을 완료 처리하지 않는다.
4. 현재 한글 글꼴은 Google Fonts `@import`에 의존한다. 서비스워커의 같은 주소 캐시만으로 외부 폰트가 오프라인에 준비됐다고 단정하지 않는다. 기존 system-ui/Georgia 대체 글꼴에서도 레이아웃·한글 인쇄가 유지되는지 확인한다. 폰트 자체 호스팅은 별도 파일·라이선스 검토가 필요한 선택이다.
5. `globals.css`와 `mobile.css` 각각의 `@media print`를 보존한다. 새 왼쪽 탐색·도구·임시 전달 패널은 `no-print` 또는 해당 인쇄 선택자로 제외하고 기록집 A4 레이아웃의 mm 단위를 화면 레이아웃 편의로 바꾸지 않는다.

## 8. 기존 검사 실행 경로와 필요한 추가 검증

아래는 **읽어서 확인한 명령과 범위**이며 이번 조사에서 실행하지 않았다.

| 명령·설정 | 실제 포함 범위 | 이번 변경과의 연결 |
|---|---|---|
| `npm test` | Vitest `tests/**/*.test.ts` | 저장·백업·출판·위치·클라우드·AI 기존 계약; 새 transfers 단위 검사는 동일 패턴 사용 가능 |
| `npm run typecheck` | TypeScript `tsc --noEmit` | 컴포넌트 props·API 계약·새 암호화 데이터 타입 |
| `npm run test:e2e` | `playwright.config.ts`, `tests/e2e`, 포트 3107 | Studio·모바일·기존 통합; 제안 board/transfers 브라우저 검사를 여기 배치 |
| `npm run test:app` | `app.playwright.config.ts`, 루트 `app-platform.spec.ts`·`web-camera.spec.ts`, 포트 3110 | 카메라·후보 처리·취소·미설정·동작 감소. `test:e2e`만 실행하면 이 검사는 빠진다 |
| `npm run build` | Next 정적 export + `scripts/build-offline.mjs` | `/`, `/board/`, `/mobile/`와 신규 수신 경로가 산출물에 포함되는지 확인 |
| `NEXT_PUBLIC_BASE_PATH=/nature-lens npm run build` 후 `npm run test:production` | 현 `production-smoke.mjs`는 `/nature-lens`와 포트 3108을 고정 | 기존 Pages 경로/오프라인/실제 PDF. Cloudflare 루트 산출물 검증을 대신하지 못한다 |

기존 production smoke는 같은 파일에 기록집 PDF·예시 저널 PDF·최초 오프라인 보드 방문·가상 카메라 저장·manifest를 연속 검사한다. 레이블을 바꾸면 해당 검사를 행동 기준으로 같이 수정하되 PDF 페이지 수나 저장 보존 검사를 삭제하지 않는다. 같은 포트/빌드 디렉터리에 의존하는 검사는 다른 작업자와 동시에 실행하지 않는다.

추가해야 할 실제 검증은 Cloudflare **루트 기준 산출물**의 정적 링크·manifest·오프라인 진입과 `/api/*` 캐시 제외, 보드 모든 필터의 초기화, 1440/390px 상세와 탐색, API 미설정이 로컬 기록을 막지 않는 동작, 작은 백업의 두 브라우저 암호화 전달/복원/삭제다. `public/sw.js`는 현재 같은 주소의 성공 GET을 넓게 캐시하므로 일반 UI 작업만으로 이 위험이 해결됐다고 보고하지 않는다. `/api/*`는 캐시·정적 HTML 대체 대상에서 제외하는 변경을 SW 담당자가 구현·검증한다.

향후 UI 파일을 실제 수정할 때는 프로젝트의 expect 스킬에 따른 브라우저 검수도 수행한다. 현재 문서 작업에는 `.tsx/.css/.html` 변경이 없다. 가상 카메라 통과는 실제 Mac Safari/Chrome 카메라·인쇄·다운로드 실기기 검증과 구분해 인계한다.

## 9. 인계 완료 판정

확정 계획을 받은 구현자는 이 지도에서 실제 변경 파일과 검사 항목을 골라 작업할 수 있다. 이번 완료는 구조·보존 계약·검사 연결의 문서화이며, 전문적인 새 화면이나 임시 전달 기능의 구현 완료를 뜻하지 않는다. 제품 코드·설정·패키지·기존 문서에는 이 조사로 인한 변경이 없다.
